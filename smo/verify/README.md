## 为什么现在就建这一层

Metal 重放（`nvn_mtl.m` 在参考项目里 626 KB）是剩下最大的一块。在没有回归闸门的情况下
往里堆代码，出了图像错误会无从二分。所以先把入口和目录立起来，Metal 的两项先占位。

## `nvn_opaque_check.py` —— 检查一条我们独有的设计前提

本仓的 `smo/gfx/nvn/nvn_state.c` 做了一个和参考项目不同的选择：**宿主状态全部放在宿主侧的
开放寻址表里，客体的 NVN 对象被当作不透明句柄，一个字节都不写**。理由是我们手上的 `nvn.h`
是 h1k421 从 *Darksiders II* 的 DWARF 重建的（NVN 53.105），版本未必与 SMO 一致，拿它的
结构布局去读写客体内存是不安全的。

这个选择更稳，但隐含一条前提：**客体（AGL）自己也不直接读 NVN 对象里的字段** ——
它只通过 `nvnXxxGetYyy()` 取值。如果 AGL 有任何地方绕过 getter 直接读结构体成员
（比如直接读 `NVNtexture` 里的 width），那么宿主侧的状态表就填不到它，游戏会读到
未初始化的客体内存。

本工具在 `main.bin` 上找这种裸访问：对每个 NVN 调用点，定位对象指针所在的寄存器，
在调用点前后的窗口里看这个寄存器有没有被带偏移地 `ldr`/`str`。

**用法**

```bash
python smo/verify/nvn_opaque_check.py            # 摘要
python smo/verify/nvn_opaque_check.py --list     # 逐条列出可疑点
python smo/verify/nvn_opaque_check.py --tsv out.tsv
```

**实测结果（`main.bin`，1706 处 NVN 调用点）**

```
调用点覆盖：已检查 1012/1706（59%）= 寄存器直传 755 + 内嵌子对象 257
  跳过 320 处栈上临时对象（AGL 自己的 builder，与本前提无关）
  跳过 374 处指针从内存取出、基址表达式追不动的  ← 盲区
已检查的调用点里，带偏移访问 733 条：
  fetch(取指针) 14 · before(对象之前) 663 · outside(超出对象) 56 · INSIDE(落在对象内) 0
```

**0 条反例**。那 663 条 `before` 是关键证据：NVN 对象大量以**内嵌子对象**的形式待在 AGL 的
大对象里（`add x0, x19, #0x48` 这种形状，257 处），AGL 读的是它自己在 NVN 对象**之前**的字段。
这正是「AGL 把 NVN 对象当不透明块、自己的状态放在旁边」的样子 —— 和我们的设计假设一致。

**分流是怎么做的**（每一档都对应一种实测形状，不是拍脑袋的白名单）

| 判定 | 含义 | 为什么不算违规 |
|---|---|---|
| `fetch` | `ldr x19,[x19,#0xc0]` 之后 `mov x0,x19` | 这是**取出** NVN 指针，读的是 AGL 包装对象 |
| `before` | 内嵌子对象基准之前（rel < 0） | AGL 自己的字段，在 NVN 对象起点之前 |
| `outside` | 超出对象大小（rel >= size） | AGL 紧随 NVN 对象之后的字段 |
| `INSIDE` | 落在 `[0, size)` 内 | **真正的反例** |

对象大小取自 `nvn.h` 的 `char reserved[N]`。注意这里**只**把它当分流尺度（判断偏移是否
明显落在对象外），没有用它的字段布局 —— 那条红线仍在。

**踩过的三个假阳性**（都已修掉并进了自检）

1. 偏移 0 的 `ldr x9,[x19]` 算成读字段 —— 那是解引用指针本身。
2. `add x0, x22, #0x48` 之前的 `x0` 是**另一个值**，拿它找出来的访问全是噪声
   （原先一律跳过，导致覆盖率只有 42%；现在识别成内嵌子对象并换算基准）。
3. 窗口里 `ldr x23,[x8]` 把基址寄存器**重新定义**了，之前的访问针对旧值
   （实测 `0xa0b9b4` 那处，是最后一个消掉的 INSIDE）。

**它能证明什么、不能证明什么**（重要，别过度解读）

- 能：在已检查的 1012 处调用点的**局部窗口**内，没有「刚传给 NVN 的那个对象」被当结构体读写。
- 不能：这不是全程数据流分析。那 374 处追不动的是明确的盲区；对象指针也可能被存进 AGL 成员、
  过很久在别的函数里再解引用，那种情况本工具看不到。

结论因此是「**没有发现反例**」，不是「证明不存在」。真正的终局判据是真机：
`nvn_state.c` 查不到就记一行 miss 日志，真机跑一遍就知道有没有漏。

## `nvn_opaque_selftest.py` —— 检查器自己的自检

一个只会说「通过」的检查没有价值。自检用**手工编码的 aarch64 指令序列**喂进被测函数，
断言每种形状都被判成预期类别 —— 包括一条真正违规的（读 NVN 对象内部必须报 `INSIDE`）。
12 个用例 / 16 条断言，不需要游戏文件：

```bash
python smo/verify/nvn_opaque_selftest.py      # 16/16
```

## `regress.sh` —— 回归总入口

```bash
smo/verify/regress.sh           # 跑所有能跑的（缺产物的自动跳过）
smo/verify/regress.sh --quick   # 只跑不需要游戏文件的那一档
```

失败不提前退出，一次看清所有坏掉的地方；退出码 = 失败项数。
本机实测：**通过 11 · 失败 0 · 跳过 3**（跳过的是 C 单测——本机没 clang——与等 Metal 的两项）。
